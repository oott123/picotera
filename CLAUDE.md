## Working Conventions

- **No unsolicited compatibility layers.** When planning or making decisions, do not introduce compatibility shims, fallbacks, deprecated-path branches, or any code whose purpose is to preserve old behavior — unless the user explicitly asks for it. Prefer clean replacements that update all call sites. If you genuinely believe a compatibility layer is unavoidable or strongly warranted, **stop and ask the user before writing it**.
- **Fail fast on input; do not be lenient.** Do not add forgiving normalization of user/API input — no silent trimming of whitespace, no case-folding, no coercing empty strings to defaults, no "did you mean" guessing, no accepting near-miss formats. Validate strictly and reject invalid input with a clear error. Only relax this when the user explicitly asks for it.

## Build & Run Commands

Toolchain is pinned via `mise.toml` (go, node, pnpm, sqlc). The `[tasks]` block in `mise.toml` defines shortcuts; direct commands also work.

```bash
# Backend
mise run server                         # go run ./cmd/picotera/main.go (auto-builds llmbridge plugin first)
go build -o picotera ./cmd/picotera     # build binary

# llmbridge cross-format converter plugin
mise run llmbridge-plugin               # go build → dist/picotera-llmbridge-plugin

# Infra (Postgres on :34052, KeyDB/Redis on :34051, MinIO on :34050)
docker compose up -d

# sqlc — edit db/queries/*.sql, then regenerate pkg/db/
sqlc generate

# OpenAPI spec (checked in at openapi.yaml, consumed by dashboard via openapi-typescript)
mise run openapi                        # writes openapi.yaml from `picotera openapi` subcommand

# Dashboard (pnpm workspace, Vue beta pinned in pnpm-workspace.yaml)
mise run web                            # pnpm --dir dashboard dev
pnpm --dir dashboard build              # type-check + vite build
pnpm --dir dashboard lint               # oxlint + eslint, both with --fix
pnpm --dir dashboard type-check         # vue-tsc --build
pnpm --dir dashboard format             # oxfmt src/
pnpm --dir dashboard generate-openapi   # regenerate TS types from openapi.yaml
```

### Nix packages

Root `flake.nix` packages the release artifacts. `.nix/flake.nix` stays the devshell, so `nix develop` still has to point at `.nix/` (as `.envrc` does). The three `third_party/` trees go.mod `replace`s come in as inputs (`flake = false`, no flake needed) from the same repositories `.gitmodules` lists, so a checkout without submodules builds and Nix ≥ 2.27 is no longer required. Their revisions live in `flake.lock` (`nix flake update` bumps them); a bumped revision that changes the vendored content invalidates `vendorHash`, which the failed build prints.

```bash
nix build                               # packages.default = picotera
nix build .#picotera                    # symlinkJoin of the two binaries below
nix build .#picotera-core               # go binary with dashboard/dist embedded
nix build .#picotera-llmbridge-plugin   # cross-format converter plugin
nix build .#picotera-dashboard          # dashboard/dist on its own
```

`packages.default` sets `PICOTERA_LLMBRIDGE_PLUGIN_PATH` to the plugin's store path with `--set-default`, so a deployment can still override it. The dashboard is built by `vite build` alone (no `vue-tsc`) and neither Go package runs tests (`doCheck = false`).

Two fixed-output hashes are maintained by hand: `pnpmDeps.hash` follows `pnpm-lock.yaml`, `vendorHash` follows `go.mod` / `go.sum` and the three `third_party/` trees (i.e. those input revisions in `flake.lock`). A stale hash fails the build and prints the value to use.

### OpenAPI → TypeScript SDK workflow

The dashboard does not call the API by hand-written client code; types and the fetch client are generated from the spec.

1. Edit Huma operations / contract types in `pkg/contract/` (and any handlers in `pkg/server/`).
2. Run `mise run openapi` — this invokes `go run ./cmd/picotera/main.go openapi` (the `openapi` subcommand on the `humacli` entry point) and writes the result to `openapi.yaml` at the repo root.
3. Run `pnpm --dir dashboard generate-openapi` — `openapi-typescript` consumes the YAML and emits `dashboard/src/openapi-types.d.ts`. `dashboard/src/api/index.ts` re-exports the schema types; `dashboard/src/api/plugin.ts` wires `openapi-fetch` against those types and installs it on the Vue app.

Always run both steps after touching a contract — backend changes are invisible to the dashboard until the TS types regenerate.

Go tests live under `pkg/llmbridge/` (bridge format conversions) and `pkg/server/` (gateway flow/helpers, overview, pricing match, project extraction, request/response decompression, web-search loops, unified-handler helpers, and more). They are pure unit tests over hand-built structs — there is no postgres-backed test harness, so DB-touching code paths are not exercised end-to-end. No Go linter is configured. Dashboard lints via oxlint+eslint.

## Bundling the dashboard

The Go binary embeds `pkg/server/static/dist/` via `//go:embed`. By default that directory only contains a placeholder `index.html` (committed) explaining how to bundle the real dashboard — `go build` works on a clean checkout without running any frontend build. Production assembly (Dockerfile / nix build) is responsible for overwriting the placeholder with `dashboard/dist/` output.

To test the bundled binary locally: `pnpm --dir dashboard build && find pkg/server/static/dist -mindepth 1 ! -name index.html ! -name .gitignore -delete && cp -r dashboard/dist/. pkg/server/static/dist/`. The directory has a local `.gitignore` (`pkg/server/static/dist/.gitignore`) that ignores everything except the placeholder, so populated assets won't accidentally get committed.

## Architecture

PicoTera is an API gateway that routes LLM inference requests across multiple providers. It exposes a management API for configuring providers, models, and endpoints.

**Stack**: Go 1.26, Huma v2 (REST framework) + Chi router, PostgreSQL via pgx, sqlc for type-safe queries, goose for migrations, Viper for config.

**Startup flow**: Parse config → run goose migrations → connect PostgreSQL → register Huma operations → mount gateway handler → serve HTTP.

### Package Layout

- `cmd/picotera/` — CLI entry point (humacli + cobra). Subcommands: `openapi` (prints spec to stdout), `set-admin <user-id>` (flips `is_admin`), `bind-identity <provider> <identity> <user-id>` (maps an auth identity to an existing user — e.g. `bind-identity http-header root 1`).
- `db/migrations/` — goose SQL migrations (embedded in binary). Schema is the source of truth.
- `db/queries/` — sqlc query definitions. **Edit these, then run `sqlc generate`**.
- `pkg/db/` — **Generated by sqlc. Never edit manually.** Contains models, queries, and `Querier` interface.
- `pkg/contract/` — Huma request/response types and operation definitions. Each resource has `To*View`/`From*View` conversion functions between DB models and API views.
- `pkg/server/` — HTTP server, operation handlers (methods on `*Server`), gateway handler.
- `pkg/server/static/` — embedded dashboard SPA (`//go:embed all:dist`). Assets are gzip+brotli precompressed at startup; served as a fallback when the LLM gateway can't match the request path. See "Bundling the dashboard" below.
- `pkg/configx/` — Viper config parsing (env vars with `PICOTERA_` prefix).
- `pkg/errorx/` — Custom error types with structured codes.
- `pkg/logx/` — logrus wrapper.
- `pkg/jsx/` — embedded JavaScript runtime (built on `github.com/fastschema/qjs`) that runs user-supplied scripts as request-lifecycle hooks. See "Scripts" below.
- `pkg/llmbridge/` — adapter types and interfaces for cross-format LLM payload conversion (Anthropic Messages, OpenAI Chat Completions, OpenAI Responses, Gemini GenerateContent). The host talks to the converter through a HashiCorp go-plugin gRPC process.
- `pkg/llmbridgeimpl/` — concrete implementations of `llmbridge` converters, compiled into the plugin target (`cmd/picotera-llmbridge-plugin`). Depends on `github.com/looplj/axonhub/llm` (LGPL-3.0; attribution in `THIRD_PARTY_NOTICES.md`).
- `pkg/kv/` — key-value store abstraction with memory and Redis (KeyDB) backends. Used by user-supplied scripts. CRUD exposed at `/api/picotera/kv`.
- `pkg/artifacts/` — request/response payload serialization. Stores bodies as zstd-compressed JSON with optional line-by-line SSE timings. MinIO-backed via the `picotera-artifacts` bucket.
- `pkg/pricing/` — model pricing calculation and matching logic.
- `pkg/annotations/` — request annotation parsing and handling.
- `pkg/transform/` — generic data transformation utilities.
- `pkg/auth/` — management-API authentication middleware + identity resolver. See "User authentication" and "User isolation & authorization" below.

### Scripts (user JS hooks)

Operators store JS source in the `script` table (CRUD via `/api/picotera/scripts`, dashboard at `ScriptsView.vue` + `ScriptForm.vue`). On each gateway request, `Server.jsxEngine` (configured in `pkg/server/server.go` from `PICOTERA_JS_*` env vars: hook timeout, memory limit, max total attempts, max delay) opens a per-request `jsx.Session`, loads the embedded `pkg/jsx/sdk.js` to install `globalThis.picotera`, then evaluates every enabled script. Scripts call `picotera.hooks.<name>.tap(name, fn, priority)` to register handlers on ten waterfalls:

- `sortProviders` — reorder/filter provider candidates before dispatch.
- `beforeMetaRequest` — runs once between `sortProviders` and the first upstream attempt (`gatewayFlow.run()`; also when sorting left zero candidates, and never on the fetch-models path). The waterfall seed is `undefined`: a tap returning `undefined`/`null` passes through, and a returned `jsx.ResponseShape` (`{statusCode, headers?, body?, tokens?}`) short-circuits the whole request — the gateway writes that response and **no upstream row is ever inserted**. The contract is strict and validated in the glue IIFE (`RunBeforeMetaRequest`, re-checked host-side): `statusCode` must be an integer in `[100, 599]`; `headers` values must be `string`/`string[]` and may not be `Content-Length`/`Transfer-Encoding`; `body` must be a string (verbatim bytes), an object/array (`JSON.stringify`d — a body Proxy is fully materialized, no marker protocol), or absent; `tokens` may only carry the five known `*Tokens` keys with integers in `[0, int32max]`. Like `sortProviders`/`beforeRequest` — and unlike the observational `afterUpstreamError`/`requestFinished` — a tap error, validation failure, or timeout goes through `failHook` (502, 503 on timeout) and no provider is tried. The body crosses out-of-band via `globalThis.__picotera_bmr_out` (same trick as `rewriteRequest`) so a large body isn't re-escaped. Recording (`gateway_flow_script_response.go`): `respondScriptResponse` writes the response (non-empty body defaults to `application/json` when the script set no `Content-Type`) and terminates the meta row via `updateMeta` + `newRequestUpdate` rather than `failMeta`, because a 2xx must leave `error_message` NULL — `finish_reason` is `3` (EOF) for 2xx and `1` (internal) otherwise, with the response body as `error_message` only in the latter case. The five token columns are written only for the counters the script reported (an explicit `0` is distinct from omitted), and only then is `costsFor` consulted for `model_cost`; `provider_id` / `upstream_model` / `ttft_ms` stay NULL. Because success-rate stats need `finish_reason = 3` **and** `output_tokens != 0`, a 2xx fast response counts as a success only when the script reported a non-zero `outputTokens` — otherwise it lands in "empty reply"; not compensated for. `ctx` deliberately exposes no candidate list or count here: a script that needs "no providers available" stashes it on a custom `ctx` field from its `sortProviders` tap.
- `rewriteModel` — rewrite the requested model name once, between extraction and provider resolution.
- `beforeRequest` — inspect / delay / skip an attempt; can override `upstreamModel` for that attempt.
- `beforeTransform` — choose or customize the outbound llmbridge profile before cross-format request conversion.
- `rewriteRequest` — mutate the pending upstream URL/headers/body just before send. Also runs once on the fetch-models path, over the upstream `/models` GET (`ctx.endpointType = "fetchModels"`, no `pending.body` since the request has no body — a script that needs one must return a whole new pending object), on the same session as `rewriteProviderModels`.
- `rewriteProviderModels` — rewrite a provider's `providerModels` array based on an upstream `/models` response (used by the "fetch models" flow in `ProviderForm`). Shares its session and `ctx.endpointType = "fetchModels"` with the `rewriteRequest` tap that ran just before it over the same `/models` fetch — a script can stash state on `ctx` in one and read it in the other.
- `afterUpstreamError` — runs after **every** failed upstream attempt (HTTP non-200, connection/network failure, decode/bridge failure, and in-stream SSE errors). Input `{ break, statusCode, message, streamed }`; output `{ break, statusCode, message }`. When `break=true` **and** `streamed=false` (the response hasn't started writing yet), the gateway stops trying further providers and writes the downstream response: `statusCode<=0` follows the upstream's original status (falling back to `502`), `message==""` follows the upstream's original body + `Content-Type` (overrides write the `message` bytes as `application/json`). For in-stream errors (HTTP 200 + SSE error event) the response has already streamed, so `streamed=true` and `break` is ignored — the hook still runs for observation (logging/kv). A **200 response body that refuses to produce content** counts as one of these: `ResponseExtractor.detectRefusal` treats an Anthropic `stop_reason = "refusal"` (streaming `message_delta`'s `delta.stop_reason`, or a non-stream body's top-level field) as a stream error, using `stop_details.explanation` (or the bare string `refusal`) as the message — so the row records `FinishReasonStreamError` with the upstream's real 200 status, tokens and cost intact, and the hook fires with `streamed=true`. When the upstream status code is exactly `400` and `streamed=false`, the input `break` seed defaults to `true` (so an unhandled upstream 400 is passed through to the client by default); every other status defaults to `false`. The hook reads this default in `input.break` and can return `{ break: false }` to keep trying further providers. `statusCode` is integer-cast; a non-string `message` becomes `""`. The hook is advisory: if it errors/times out it is logged and treated as `break=false`. `ctx.attempt.lastError` (`{providerId, statusCode, message}`) is set before the hook runs and, absent a `break`, carries into the next attempt's `beforeRequest`. The hook's `rewriteRequest`/`beforeRequest` JS errors (including timeout-tainted sessions) do **not** trigger it — those keep the existing `failHook` behavior.
- `getToolUsageCost` — runs once per **successful** request, after the upstream response was read and before the two request rows are written (`resolveToolUsageCost` in `gateway_flow_tool_cost.go`, called from `completeGatewaySuccess` and `unifiedStreamSuccess`). Input and output are both `jsx.ToolUsageCostView` — `{ toolUsage, usageRaw, toolUsageRaw, toolCost, toolCostCurrency }` — seeded with the extractor's normalized usage (`[]` when the upstream reported none, so a tap can iterate unconditionally), the two raw objects (`null` when the upstream reported none — `rawOrNull` in `session.go` normalizes an empty `RawMessage`), `toolCost: null` and `toolCostCurrency: ""`; the server never computes a tool cost of its own. `usageRaw` / `toolUsageRaw` are **read-only**, structurally rather than by validation: the glue IIFE rebuilds the result from `toolUsage` / `toolCost` / `toolCostCurrency` alone, so a tap returning them (e.g. `{...input, toolCost: 1}`) neither errors nor takes effect, and the columns are written from `ResponseMetrics` regardless. Passthrough is `undefined` / `null` / `ctx` / the unchanged input object, and the script's output is what gets recorded — returning `toolUsage: []` clears the extracted usage to SQL NULL. Validated strictly in the glue IIFE (`RunGetToolUsageCost`) and re-checked host-side by `validateToolUsageCost`, with **no coercion**: the result must be a non-array object; `toolUsage` must be an array of objects whose keys come from the `name` / `model` / `numRequests` / `inputTokens` / `outputTokens` / `numImages` whitelist (an unknown key is an error — a typo would silently drop billing data); `name` is a non-empty string, `model` a string when present, each counter a non-negative safe integer when present; `toolCost` is `null`/absent (no cost) or a finite number in `[0, 1e14)` (the `NUMERIC(20, 6)` integer part is 14 digits); `toolCostCurrency` must be a non-empty string exactly when `toolCost` is a number, and is never checked against `exchange_rate` (same as pricing writing `p.Currency` through). `marshalToolUsage` then applies the extractor's own all-zero-entry drop to the script's output too, and `toolCostToNumeric` runs the cost through `ratToNumeric6` for `model_cost`-identical precision; one hook result is written to **both** the meta and upstream rows. Unlike `beforeMetaRequest` the hook is advisory (`afterUpstreamError`-style): a tap error, validation failure, or a timeout-tainted session is a warn-level logx line and falls back to the extracted usage with both cost columns NULL — the response has already been sent, and the finish reason stays untouched so a scripting mistake never reads as an upstream failure. Failure paths and `beforeMetaRequest` short-circuits never run it: there is no upstream response, hence no usage.
- `requestFinished` — runs once per gateway/unified request after the meta row's finish reason landed in the DB and before the session's VM is destroyed. Purely observational: the waterfall's return value is discarded (typical uses: usage accounting, outcome-based annotations). Input is `jsx.RequestFinishedView` — `{ requestId, statusCode, finishReason, errorMessage, timeSpentMs, ttftMs, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, cacheWrite1hTokens, modelCost, modelCostCurrency, toolCost, toolCostCurrency, providerId, model, upstreamModel, toolUsage, usageRaw, toolUsageRaw }`, entirely from the in-memory `gatewayFlow.metaFinal` snapshot (never read back from the DB); fields that never happened are zero. `toolUsage` is the one exception to "zero": it is **always an array** (`[]` when the upstream reported nothing), so a tap can iterate it unconditionally — it crosses as the `json.RawMessage` of the exact bytes written to the `tool_usage` column, inlined verbatim by `mustJSON`, so the jsx layer defines no entry type of its own. `usageRaw` / `toolUsageRaw` cross the same way but keep `null` for "not reported" rather than adopting the always-an-array convention — a raw object is of arbitrary shape, where `{}` and absent are different facts. Because the raw columns are only written on the success paths, a failed request's hook always sees two `null`s. The three tool fields therefore carry whatever `getToolUsageCost` committed (`0` / `""` / `[]` when it committed nothing), since that hook runs before the row is written and this one after. The snapshot is accumulated by `gatewayFlow.updateMeta`, the wrapper **every** meta-row update goes through (`gateway_flow.go`, `gateway_flow_errors.go`, `gateway_flow_success.go`, `gateway_unified_helpers.go` — upstream rows still call `updateRequest` directly), so `metaOutcome.merge` mirrors each partial update column-by-column. Two known edges, by convention and not compensated for: a request that fails *before* `resolveAndRewriteModel` has no VM, so the hook never fires; and the meta response artifact is uploaded before this point, so `console.*` output from this hook reaches logx but not the artifact's log list.

Hooks are run as priority-sorted waterfalls (higher priority first); each tap may return a value that becomes the input to the next tap, or `undefined` to pass through. JS-visible context shapes are defined in `pkg/jsx/types.go` (`Candidate`, `RequestShape`, `BeforeRequestInput`, `RewriteInput`, `ProviderSummary`, etc.) — provider credentials are deliberately stripped before crossing the JS boundary. Scripts also get `picotera.fetch(url, init)` (host-side fetch returning parsed JSON) and a `console` shim that captures up to 1000 entries / 256 KiB per session into `LogEntry` records persisted alongside the request.

**Body Proxies (`pkg/jsx/objects.go` + `sdk.js`).** The two large request bodies a hook can touch — `ctx.request.body` and rewriteRequest's `pending.body` — are NOT eagerly embedded as JS objects. They live as `pkg/jsonast` `*Node` trees on the Go side; `sdk.js` wraps each accessed object/array node in a `Proxy` keyed by an integer id whose get/set/enumerate/delete traps forward through the synchronous `__picotera_obj_*` host functions. So a scalar (e.g. a multi-MiB data-url) crosses into QuickJS only when a script reads that field, and writes land straight on the Go tree — keeping memory flat for large bodies that would otherwise blow the JS memory limit on an embed→parse→re-stringify round-trip. The session installs `ctx.request.body` via `Session.SetClientBody([]byte)` (call it after any PatchContext that sets `request`; re-calling it after the model rewrite changes the body invalidates the prior Proxy); `RunRewriteRequest(initial, body []byte)` installs `pending.body` and returns the final upstream bytes (nil = fall back to pre-hook bytes, including the byte-identical clean-passthrough case). A hook that never touches the body never parses it. Script-visible semantics: nested reads return cached child Proxies (`body.a === body.a`); `Array.isArray`/`map`/`filter`/`slice`/spread/`Object.keys`/`JSON.stringify` and the array mutators all work; assigning a plain object or another Proxy deep-copies it into the tree (no aliasing); writing `undefined`/functions, out-of-range array writes, deleting a non-last array element, or growing `length` all throw; a stale Proxy (used after its body tree was replaced) throws. Array Proxies carry a `ProxiedArray` prototype (`target → ProxiedArrayProto → Array.prototype`) whose mutators — `splice`/`push`/`pop`/`shift`/`unshift`/`reverse` — route through `__picotera_arr_splice` / `__picotera_arr_reverse` so the Go side reorders the `[]*Node` slice by pointer: existing elements that merely shift position are **relocated, never cloned** (a Proxy passed as an inserted item is still deep-copied, matching the set path). `sort` (needs a JS comparator) keeps the native `Array.prototype` implementation and so still clones via per-index set traps. There is **no** data-url masking at the JS boundary — scripts read originals. (The `pkg/datamask` package still exists on disk but is unwired: nothing imports it, and no `PICOTERA_JS_DATA_URL_MASK_*` env var is read.)

**Annotation API + request refs (`pkg/jsx/helpers.go` `registerHostAPI` + `pkg/server/jsx_host.go`).** Scripts tag rows through an explicit id-keyed SDK, not through a writable map on `ctx`: `picotera.request.setAnnotation(requestId, key, value)`, `picotera.provider.setAnnotation(providerId, key, value)`, `picotera.apiKey.setAnnotation(apiKeyId, key, value)`, plus the read side `picotera.provider.get(providerId)` / `picotera.apiKey.get(apiKeyId)` (returning the same credential-free `ProviderSummary` / `ApiKeySummary` shapes as `ctx.provider` / `ctx.apiKey`, or `null` for a missing id — same miss semantics as `picotera.kv.get`). Distinct from `ctx.annotations`, which remains the read-only *merged config-layer* view of model/provider/apiKey annotations. **Strict typing (fail fast), validated in `sdk.js` before the host boundary:** `requestId` must be a non-empty string, `providerId`/`apiKeyId` must satisfy `Number.isInteger`, `key` must be a non-empty string, and `value` must be a string (empty string included) or `null`/`undefined` to delete the key — any other type is a `TypeError`, with no implicit `String()` coercion; the Go side re-checks the key defensively. Values cross as JSON (`""` = delete) so an empty-string value stays distinguishable from a delete. `setAnnotation` on a nonexistent id **throws** (`request %q not found` etc., from the `:execrows` 0-row check); `get` on a nonexistent id returns `null`. Each host call is a synchronous DB write on `context.WithTimeout(context.WithoutCancel(ctx), 5s)` — detached from cancellation so a `requestFinished` annotation still lands after the client disconnected or the dashboard interrupted, and the 5s bound is the only backstop (the hook timeout cannot interrupt a blocking host function). Cost model matches kv/fetch: one DB round-trip per key, so hot-path scripts should not loop over these. Provider/api-key annotation writes affect **subsequent** requests' merged `ctx.annotations`; the current session's already-patched snapshot is not refreshed. `ctx.metaRequest` / `ctx.upstreamRequest` are read-only identity refs (`jsx.RequestRef`: `{ id, spanId, parentSpanId, traceId }`, with `parentSpanId`/`traceId` `null` when absent) that a script pairs with `setAnnotation`. Both start as `null`; `ctx.metaRequest` is patched in post-auth (so `traceId` is the `traces.id` returned by `upsertTrace`), and the fetch-models session leaves it `null` (its session id is a synthetic string matching no request row). `ctx.upstreamRequest` is reset to `null` at the top of every `runSingleAttempt` (`Session.SetUpstreamRequest(nil)`) and set to the attempt's row right after `insertUpstreamAttempt` succeeds, so `beforeRequest` never sees a row that doesn't exist yet, and `rewriteRequest` / `afterUpstreamError` / the in-stream error hook always see the current attempt.

### Key Patterns

- **Endpoint matching**: request paths are matched against `endpoint.path` patterns (which may contain `{name}` placeholders matching any non-empty string, including `/`). The matcher is an in-memory cache (`pkg/server/endpoint_router.go`) loaded lazily from `GetEndpoints` and sorted by literal-character specificity. Any mutation of the `endpoint` table **must** call `Server.endpointRouter.Invalidate()`. Do not reintroduce `GetEndpointByPath` for gateway routing — it only remains for exact-path validation in `handle_provider_endpoint.go`. The API key is now resolved **once per request at the HTTP entry point** (`Server.authenticateGatewayClient` → the `clientAuth` value passed into `newGatewayFlow`; `gatewayFlow.authenticateAndBackfill` consumes it rather than querying again) — which is what makes it available at routing time. On a **miss**, `serveRouteNotFound` consults that result: a request that authenticated successfully always gets the structured JSON 404 plus a recorded meta row (`Kind = gatewayRouteNotFound`, `endpoint_path` = the decoded path the router failed to match, no model / provider, `status_code = 404`, `error_message = "route not found"`, `finish_reason = 1`), however browser-ish its headers look; `run()` stops right after `authenticateAndBackfill`, so no JS session is created and no hook — `requestFinished` included — fires. SPA fallback is left to **unauthenticated** safe navigations only (`routeNotFoundFallsBackToSPA` = `!authenticated && looksLikeBrowserNav`), and an unauthenticated non-navigation still gets the unrecorded JSON 404 — a bad or missing key on a nonexistent path reports "no such route", never 401/403.
- **Prefix matching** (`endpoint.prefix_match`): a prefix endpoint's `path` is a prefix rather than a whole path. It matches iff the request path starts with `path + "/"` — the bare prefix itself does **not** match, and falls through to 404 / the SPA. `Match` returns the remainder as a `suffix` (always `/`-leading and non-empty); ordinary endpoints return `""`. No new sort rule is needed: a prefix entry's `literalLen` is just `len(path)`, so an exact endpoint mounted under the same prefix always outranks it. Routing matches the decoded `r.URL.Path`, but `handle_gateway.go` re-cuts the suffix off `r.URL.EscapedPath()` at the same byte offset so the upstream sees the client's exact escaping (a mismatch ⇒ 404); `handleUpsertEndpoint` guarantees the offsets agree by rejecting a prefix path that contains `{`/`}`, ends with `/`, or carries `%` / non-ASCII bytes. The suffix follows the **candidate**, not the request: `gatewayCandidateSidecar.AppendPath` is set only for a candidate whose endpoint row has `prefix_match`, so a bridged non-prefix candidate serving the same unified request keeps its URL untouched. `buildUpstreamRequest` inserts it before the upstream URL's first `?` / `#` (so `…/v1?api-version=x` + `/responses` → `…/v1/responses?api-version=x`), *before* the `rewriteRequest` hook, so scripts see the final `pending.url`. `gatewayFlowConfig.RecordedEndpointPath` (prefix + suffix) is what the meta row records; `sidecar.EndpointPath` (also prefix + suffix) is what the upstream row records; `config.Endpoint` stays the raw DB row because `resolveProviders` looks candidates up by its path. JS-side, `ctx.endpoint.path` remains the configured prefix — a script wanting the concrete path reads `ctx.request.path`. The `codex` endpoint type **must** enable it (400 otherwise): one codex endpoint row represents one Codex upstream's `base_url`, and `/responses`, `/responses/compact`, `/alpha/search` … are just suffixes. Because request rows record the concrete sub-path while the endpoint label list only carries the prefix, `ListRequests`' `endpoint_path` filter is prefix-aware — `= $n OR starts_with(endpoint_path, $n || '/')` (`starts_with`, not `LIKE`, so `%` / `_` in the value aren't wildcards); the dashboard mirrors this with a longest-prefix name fallback (`longestPrefixName` in `requestLabels.ts`). Because a prefix endpoint's sub-paths are open-ended and some of them (`/alpha/search`, `/responses/compact` …) carry no model at all, `extractModel`'s body branch takes an `optional` flag set from `endpoint.PrefixMatch`: an **absent** `modelPath` field routes as no-model (the same `GetProvidersByEndpoint` path an endpoint with `model_path = ""` takes — `f.model.Routed` is `""`, the meta row's `model` is NULL, no `model_cost`, and `rewriteModel` returning a non-empty name is still a `failHook`), while a field that is present but not a non-empty string (`""`, `null`, a number, an object) is still a 400 `MODEL_NOT_FOUND` — the degradation covers "this sub-path has no model", not bad input. It covers the body branch only: `handleUpsertEndpoint` rejects a prefix endpoint whose `modelPath` is a `{name}` path variable, since a prefix path carries no variables and the endpoint could never resolve one.
- **Project matching**: every gateway request body is scanned by `pkg/server/project_extractor.go` against some fixed regexes. Captures are JSON-string unescaped, expanded into separator-aligned ancestors, and matched via the synchronous `MatchProjectByPaths` SQL query; there is no project-router memory cache. Projects are **per-user** (`project.user_id`, unique `(user_id, name)`): `Extract`/`MatchProjectByPaths` take the resolved `userID` and scope matching to that user, and auto-create is gated on that user's `project.autoCreate` user-setting (absent ⇒ off). Extraction happens **after authentication** in `authenticateAndBackfill` (`gateway_flow.go`): the meta row is inserted with `project_id = NULL`, then `UpdateRequestOnHeader` backfills `project_id` alongside `user_id`. The matched `project_id` is written onto every upstream `request` row and triggers an asynchronous `UpsertProjectSeen`.
- **sqlc workflow**: Write queries in `db/queries/*.sql` → run `sqlc generate` → use generated code in `pkg/db/`. The `Querier` interface in `pkg/db/querier.go` lists all available DB methods. sqlc is configured in `sqlc.yaml` (pgx/v5 driver, `emit_interface: true`, camelCase JSON tags).
- **Adding an API operation**: Define operation + request/response types in `pkg/contract/`, add handler method on `*Server` in `pkg/server/`, register in `registerOperations()`. After the change, regenerate `openapi.yaml` so the dashboard's typed client picks it up.
- **Config**: All settings via env vars with `PICOTERA_` prefix (e.g., `PICOTERA_DATABASE_URL`, `PICOTERA_PORT`, `PICOTERA_APP_TITLE`). Default port is 9898. The dashboard title comes from `PICOTERA_APP_TITLE` and is exposed read-only via `GET /api/picotera/config` (`{ "title": ... }`).
- **API base path**: All management operations are under `/api/picotera`.
- **Database**: TimescaleDB (`timescale/timescaledb:2.26.4-pg17` image) on port 34052 via docker-compose. Migrations auto-run on startup. A MinIO instance on 34050 (bucket `picotera-artifacts`, bootstrapped by `minio-init`) backs the artifact sink (`pkg/artifacts/`).
- **`request` is a TimescaleDB hypertable** (migration 017): partitioned by `created_at` with composite primary key `(id, created_at)`. `created_at` has no column default — every insert/update/delete must supply it (see the `id_created_at` / `created_at` args in `db/queries/request.sql`). Cursor pagination tuples are `(created_at, id)`, not just `id`.

### Unified generation routes

Seven fixed chi routes plus one wildcard mount are registered as runtime constants in `server.go` BEFORE the catch-all gateway mount and back the cross-format dispatch. They live under `/api/unified` (NOT `/api/picotera`) so the user-auth middleware — which guards only the `/api/picotera` prefix — leaves them open; like the gateway they authenticate via API key:

- `POST /api/unified/v1/messages` — Anthropic Messages source.
- `POST /api/unified/v1/responses` — OpenAI Responses source.
- `POST /api/unified/v1/chat/completions` — OpenAI Chat Completions source.
- `POST /api/unified/v1beta/models/{model}:generateContent` — Gemini GenerateContent source (non-stream).
- `POST /api/unified/v1beta/models/{model}:streamGenerateContent` — Gemini GenerateContent source (stream).
- `POST /api/unified/v1/embeddings` — OpenAI Embeddings, **passthrough**, non-streaming only. Plural path so an OpenAI SDK can point `base_url` at `…/api/unified/v1`.
- `POST /api/unified/v1/messages/count_tokens` — Anthropic count_tokens, **passthrough**, non-streaming only.
- `POST /api/unified/codex/*` — the Codex mount (see below), also reachable as `POST /api/unified/backend-api/codex/*` (same mount, alias prefix).

`pkg/server/unified_routes.go` is the single source of truth and the dispatch axis is the **route**, not the format: two routes can share a format, so there is no format → path reverse lookup. Each `unifiedRoute` carries `Path` (also the meta row's `endpoint_path`), `Name`, `Format` (`FormatUnknown` for passthrough), `SourceType` (the `contract.EndpointType_*` the synthetic endpoint reports), `UpstreamSuffix` (what a prefix candidate appends to its upstream URL — empty on the fixed routes) and `Codex`. `route.passthrough()` is derived from `Format == FormatUnknown` — llmbridge having no format and there being no converter are the same fact.

**The Codex mount.** `/api/unified/codex/*` is a wildcard registration rather than a route-table entry, because Codex's sub-paths are open-ended. It is registered on **both** prefixes in `codexMountPatterns` (`unified_routes.go`): `codexMountPath` = `/api/unified/codex`, plus the alias `codexBackendAPIMountPath` = `/api/unified/backend-api/codex`, which mirrors ChatGPT's own `<host>/backend-api/codex/responses` layout so a client whose `base_url` is `…/api/unified` reaches the same handler. chi hands both registrations the same wildcard remainder, so suffix normalization, candidate resolution and the upstream URL are identical, and `codexUnifiedRoute` always builds `Path` from `codexMountPath` — the alias never appears in a **served** request's row, hence no impact on `completion_endpoint_path`, the continuous aggregates, the `endpoint_path` prefix filter or the endpoint label list. The one exception is a sub-path that fails to normalize: that 404 row is recorded at the path the client actually asked for, alias prefix included, and being outside `completion_endpoint_path` it affects none of the above. `handleUnifiedCodex` normalizes the remainder with `normalizeCodexSuffix` — a leading `/v1` segment is stripped, so a `base_url` of `…/api/unified/codex` and one of `…/api/unified/codex/v1` are equivalent; an empty result (the bare mount, a trailing slash, a bare `/v1`) goes through the shared `serveRouteNotFound`, i.e. 404 `route_not_found` plus a recorded meta row when the client authenticated (the mount only takes POST, and `corsMiddleware` answers OPTIONS first, so the SPA fallback is unreachable here) — and then builds a per-request `unifiedRoute` with `codexUnifiedRoute(suffix)`. `SourceType` is always `EndpointType_Codex` (14), which also drives `dedupeUnifiedRows`' `betterRow` so a channel configured with both a codex and an `openaiResponses` endpoint sends Codex traffic through the codex row. `Path` — hence the meta row's `endpoint_path` — is `/api/unified/codex` + the *normalized* suffix, so `/v1/responses` and `/responses` record the same value. `/responses` keeps `FormatOpenAIResponses` and can therefore bridge to Anthropic / Gemini / ChatCompletions upstreams (its candidate set is the usual four types **plus** `codex`); every other sub-path is `FormatUnknown`, i.e. codex-only passthrough. On a codex candidate the upstream format is resolved to the route's own format, so `bridging` is false and the bytes are forwarded verbatim either way. It is also the one **prefix mount** (`unifiedRoute.PrefixMount`, set only by `codexUnifiedRoute` — a field distinct from `Codex`, which is about the extra candidate type, so a future prefix mount only needs to set `PrefixMount`): a body with no `model` field routes as no-model instead of 400, exactly as on a `prefix_match` path endpoint. `resolveProvidersByTypes` then runs the sister query `GetProvidersByEndpointTypes` (same column list as `GetProvidersByEndpointTypesAndModel` with the model columns flattened to constants, projected back by `fromNoModelTypesRow`), so every non-disabled provider bound to an endpoint of one of the candidate types is a candidate, independent of `provider_models` — dedupe, validity filter and priority sort stay shared. `buildRewrittenUpstreamRequest` skips `SetBodyModel` when `UpstreamModel == ""` so a body that never had a `model` key doesn't get `"model": ""` injected; a `beforeRequest` hook can still opt in by setting `upstreamModel`. The fixed routes are not prefix mounts — a missing `model` there is still 400.

These are NOT rows in the `endpoint` table — operators only configure the underlying upstream `endpoint` rows (`anthropicMessages`, `openaiChatCompletions`, `openaiResponses`, `geminiGenerateContent`, `geminiStreamGenerateContent`, plus `openaiEmbedding`, `anthropicCountTokens` and `codex`). The unified handler (`pkg/server/handle_unified_gateway.go`) collects every candidate MPE that supports the requested model+stream tuple via `GetProvidersByEndpointTypesAndModel`, runs the gateway-generation JS hooks (same shapes as the path-based gateway, including `beforeTransform` for outbound profile selection), and per attempt: if the chosen upstream's `endpoint_type` differs from the source format, runs the body through `pkg/llmbridge/` **before** `rewriteRequest` (the hook sees and mutates the upstream-format body) and the response back before writing to the client. Identity (1:1) attempts are byte-for-byte passthrough so token/TTFT extraction is unaffected.

**Passthrough routes** (`openaiEmbedding` = 13, `anthropicCountTokens` = 5, and every codex sub-path but `/responses`) narrow this: `candidateEndpointTypes` returns the single-element set `{route.SourceType}`, so only an upstream configured with that very endpoint type can serve them (no fallback to `openaiResponses`; a miss is 404 `no_provider_available`). They use `identityPrepareAttempt`, so `beforeTransform`, web-search rewriting and llmbridge conversion are all skipped — every other hook (`sortProviders`, `beforeMetaRequest`, `rewriteModel`, `beforeRequest`, `rewriteRequest`, `afterUpstreamError`, `requestFinished`) runs as usual. Like every non-Gemini route they route on the body's `model` (missing/empty ⇒ 400 `model_not_found`), so `rewriteModel` and the `beforeRequest` `upstreamModel` override still write back through `sjson`; otherwise request and response bytes are forwarded verbatim. `unifiedStreamSuccess` still handles the success path — with `bridging=false` it degenerates to byte forwarding while keeping the route pattern on the meta row and the upstream's configured path on the upstream row. `/api/unified/v1/messages/count_tokens` is the one passthrough route whose response reports no usage at all (`{"input_tokens": N}`): the extractor produces no token fields, so all five token columns and `model_cost` stay NULL, and — being outside `completion_endpoint_path`'s whitelist — the route stays out of the success-rate / empty-reply / finish-reason stats while request-volume stats still count it.

### User authentication (`pkg/auth/`)

A chi middleware (`auth.Middleware`) authenticates the internal management API. It does **not** match a path prefix internally; instead `server.go` derives `mgmtRouter := router.With(auth.Middleware(...))` (after `decompressRequest`) and registers every `/api/picotera` route on it — the Huma management operations (`humachi.New(mgmtRouter, ...)`, which also carries Huma's own `/openapi.*` and `/docs`) plus the raw `test/direct` route. The gateway catch-all and `/api/unified` stay on the bare `router` and authenticate via API key; static assets fall through the gateway. (Because Huma's docs routes live on `mgmtRouter` too, they require auth — the dashboard generates types from the checked-in `openapi.yaml`, so nothing depends on them being open.) **Exactly one identity provider is enabled.** `configx.validateAuth` counts `auth.single_user_mode` / `auth.header_enabled` / `auth.oidc.enabled` and fails startup on 0 (`no auth provider enabled`) or more than 1 (`exactly one auth provider must be enabled`) — so `auth.Resolver.Resolve` is a single dispatch, not a precedence chain:

1. **single-user-mode** (`PICOTERA_AUTH_SINGLE_USER_MODE=true`) — ignores all headers, fixes identity `(single-user-mode, root)`, and **unconditionally** bootstraps that user as `is_admin=true` (independent of auto-create).
2. **http-header** (`PICOTERA_AUTH_HEADER_ENABLED=true`, `PICOTERA_AUTH_HEADER_NAME=<header>`) — reads the configured header; empty/missing → 401. Non-empty value is the `identity` under provider `http-header`; unknown identity creates a user only when `PICOTERA_AUTH_AUTO_CREATE_USER=true` (else 401). Startup fails fast if `HEADER_ENABLED` is set with an empty `HEADER_NAME`.
3. **oidc** (`PICOTERA_AUTH_OIDC_ENABLED=true`) — reads the session cookie; see below.

On success the resolved `*db.AppUser` is stored on the request context (`auth.WithUser`); humachi passes it through so handlers read it via `auth.UserFromContext(ctx)` (see `GET /api/picotera/me`). On failure the middleware writes `401 {"message":"unauthorized"}` directly. Two tables back this (`db/migrations/033_users.sql`): `app_user` and `user_identity` (unique `(provider, identity)`, no FK on `user_id`); auto-create is a single transaction with `ON CONFLICT DO NOTHING` + reread as a concurrency guard. A user carries a `disabled` flag: the resolver rejects a disabled user with `ErrUnauthorized` (401) on **every** provider including single-user-mode root; the gateway separately rejects requests whose API-key owner is disabled (or missing) with 403 (`gateway_helpers.go`). `GET /api/picotera/config` reports the active mode as `authMode`, which is how the dashboard decides whether an interactive logout exists.

#### The oidc mode (`session.go` / `oidc.go` / `handlers.go`)

Standard authorization code flow, sessions held in the database, cookie carrying only a session id. **It only touches the management plane** — the gateway and `/api/unified` still authenticate by API key and never read the cookie.

*Configuration.* `PICOTERA_BASE_URL` (required here, ignored elsewhere) is the base of the OAuth callback url; `PICOTERA_AUTH_OIDC_*` covers `ISSUER`, `CLIENT_ID`, `CLIENT_SECRET`, `SESSION_SECRET`, `SESSION_TTL` (default `12h`), `SCOPES` (default `openid profile email`), `AUTH_ENDPOINT` / `TOKEN_ENDPOINT` / `USERINFO_ENDPOINT`, `PKCE` (`*bool`) and `CLIENT_AUTH_METHOD` (`client_secret_basic` default, or `client_secret_post`). User auto-create reuses `PICOTERA_AUTH_AUTO_CREATE_USER` and creates non-admins, as in http-header mode. Everything is validated at startup: the credentials and session secret must be non-empty, `session_ttl > 0`, `base_url` an absolute url naming only an origin (the scheme is *not* checked — TLS termination is the operator's business), and `issuer` required, absolute and **without a trailing slash** whenever discovery is needed (the discovery url is built by concatenation, so a trailing slash is rejected rather than trimmed). With all three endpoints configured the issuer is never contacted and `pkce` must be set explicitly, because there is then nothing to infer it from.

*Protocol.* `github.com/coreos/go-oidc/v3` for metadata and userinfo, `golang.org/x/oauth2` for the code flow and PKCE. The provider bundle is built lazily on the first request that needs it and cached only on success — the IdP being down cannot keep the process from starting. Discovery infers PKCE from `code_challenge_methods_supported` (explicit config wins); a *partial* endpoint override rebuilds the provider through `oidc.ProviderConfig` **after** reading the raw document, since a ProviderConfig-built provider carries no claims to read. `client_auth_method` is mapped onto `Endpoint.AuthStyle` instead of letting oauth2 probe, which would cost a failed round trip. Identity is `UserInfo.Subject`; **the ID token is never verified or consumed** — userinfo is a direct TLS back-channel response, and code injection is already ruled out by the state cookie and PKCE. The display name (`name` → `preferred_username` → `email` → `sub`) is used only when creating the user.

*Session.* Table `user_session` (migration 051: `id TEXT PK`, `user_id`, `created_at`, `expires_at`, index on `user_id`); the id is 32 random bytes, base64url. `TouchUserSession` is one statement that reads, slides the expiry to `now + session_ttl`, and joins `app_user` — so there is no window for reading a just-expired row, a deleted user's session stops resolving by itself, and `disabled` / `is_admin` changes take effect immediately. Expired rows are dropped per user at login; there is no background sweeper. Logout deletes the row, which is what actually revokes access.

*Cookie.* One name, `__Host-Http-Picotera-Auth`, fixed to `Path=/; HttpOnly; Secure; SameSite=Lax` with no `Domain`. Encoding and encryption are `gorilla/sessions`' `CookieStore` (HMAC-SHA256 + AES); the two keys are derived from the single `session_secret` via HKDF-SHA256 with distinct info strings. The same name carries two payloads, told apart by a `k` field — `{k:"a", state, verifier, redirect}` while a login is in flight, `{k:"s", sid}` afterwards; they never coexist. Two stores share the key pair with different `MaxAge` (10 minutes for state, `session_ttl` for the session), because securecookie's expiry check lives on the codec. Always `store.New`, never `store.Get`: Get caches by cookie name per request and the two stores would read each other's decode. Any decode failure means "no session" — 401 or a login redirect, never a 500. Every authenticated management response re-issues the cookie (`Resolver.RefreshSessionCookie`) so the browser-side lifetime tracks the `expires_at` just written.

*Routes* (bare chi routes on the unguarded router, registered before the catch-all, absent from `openapi.yaml`): `GET /api/picotera/auth/login` (validates `redirect_to` as a same-site absolute path, stores state + PKCE verifier, redirects to the IdP), `GET /api/picotera/auth/callback` (constant-time state comparison, code exchange, userinfo, `resolveOrCreate`, session insert; renders a minimal HTML error page with a re-login link, since the browser arrives by navigation), `POST /api/picotera/auth/logout` (204).

*Reaching the login page.* A browser navigating to the dashboard never passes through `auth.Middleware` — it lands in the gateway's SPA fallback. `serveRouteNotFound` therefore calls `OIDC.RedirectUnauthenticatedNav` first: GET/HEAD with `Accept: text/html` and no decodable session cookie redirects to the login route; subresources fall through to the static handler unchanged. Only the cookie is checked, no database round trip — a browser holding a stale session id is caught by the next management API call, whose 401 carries `X-PicoTera-Login-Url` (set only in oidc mode, so no other mode can loop).

### User isolation & authorization

Two orthogonal layers sit on top of the resolved user:

**1. Per-resource ownership (data isolation).** Three resource classes are scoped to a `user_id` with **no admin bypass** — even admins see only their own:

- `api_key.user_id` — owner = creator (taken from context, never the request body).
- `request.user_id` (nullable) — owner = the API key's user; backfilled post-auth by `UpdateRequestOnHeader` (meta rows are inserted NULL pre-auth).
- `traces.user_id` — trace identity is the composite `(parent_span_id, user_id)`, not `parent_span_id` alone, so a client-controlled `parent_span_id` can't merge two users' traces. `UpsertTrace` runs post-auth (anchored on the meta row's `created_at`); every `ListRequestTraces` LATERAL also constrains `request.user_id = traces.user_id`.
- `project.user_id` — see "Project matching".

Read paths inject the current user as a **mandatory** SQL filter (`WHERE user_id = $N` on list; `AND user_id = $N` on single-get/filter/cross-span — a miss is a 404, never a leak). Live-progress / interrupt first re-check ownership via the user-scoped `GetRequest` before touching the in-memory `liveRequests` map. The `user_id` columns are NOT NULL with no default (except nullable `request.user_id`, which is NULL on the pre-auth meta row until backfill), so every insert must supply `user_id`; the schema assumes a user with id 1 exists (single-user-mode root). All three continuous aggregates (`request_overview_bucketed`, `request_speed_bucketed`, `request_outcome_bucketed`) carry `user_id` in their `GROUP BY`.

**2. `is_admin` capability gate (admin vs user features).** `registerOperations` (`server.go`) registers every Huma op on one of two groups sharing the `/api/picotera` prefix: `mgmt` (all authenticated users) and `admin` (`admin.UseMiddleware(s.requireAdmin)` → 403 for non-admins, 500 if context user is somehow nil). The split — see `register(mgmt, admin)`:

- **mgmt (user):** `me`, `config`, overview ×5 (`summary`, `distribution`, `series`, `speed-boxplot`, `outcome-series`), api-key ×5, request/trace ×6, **label** endpoints, **project** CRUD ×5, **user-setting** CRUD, exchange-rate *list* (read).
- **admin:** providers, models, endpoints, provider-endpoints, scripts, kv, exchange-rate writes + match-pricing, fetch-models, user/user-identity CRUD, and the **admin overview** endpoints.

The raw chi route `POST /api/picotera/test/direct` is not a Huma op, so it does its own admin check inside `handleTestDirect`. `NewHuma()` (openapi generator) calls the same `register()` so the spec never drifts from the live server. Both groups sit behind the chi-level `auth.Middleware`, so `requireAdmin` always sees a non-nil context user.

**Label endpoints** (`pkg/contract/label.go`, `handle_label.go`, mgmt group): `GET /api/picotera/labels/{providers,models,endpoints,projects}` (+ upstream-models) return minimal id/name/path projections of admin-only resources so user-facing views (overview filters, request views, gateway test) can render names without reading full configs (notably provider `credentials`). They reuse the existing list queries and project in the handler — no new sqlc.

**Admin global overview** (`pkg/contract/admin_overview.go`, `handle_admin_overview.go`, `db/queries/admin_overview.sql`, admin group, prefix `/api/picotera/admin/overview`): a parallel, cross-user copy of the user overview. Its queries mirror `overview.sql` one-for-one, the difference being they have no mandatory `user_id` filter (instead an *optional* `userId` narg) and offer a `user` dimension in place of apiKey/project. It is a separate endpoint set with its own SQL rather than a conditional on the shared user-scoped queries, so no single query carries two scope semantics.

**Request credential hygiene** (`gateway_helpers.go`): `buildUpstreamRequest` strips the local auth header (`config.Auth.HeaderName`) in addition to the fixed credential headers so a client/proxy can't leak it upstream; `redactRequestCredentials` rewrites `Authorization`/`X-Api-Key`/`X-Goog-Api-Key`/`Cf-Access-Client-Id`/`Cf-Access-Client-Secret`/`?key=` to `[REDACTED]` on the **artifact copy only** (the real requests keep live creds). The dashboard's session cookie gets the same two-step treatment on the `Cookie` header, matched by exact name with the client's other cookies left alone: `stripPicoteraCookie` removes the pair from the upstream request entirely (dropping the header when nothing is left), and `redactPicoteraCookieValue` replaces just its value in the artifact copy — so the meta artifact (client → PicoTera, where the cookie appears) shows `__Host-Http-Picotera-Auth=[REDACTED]` alongside the untouched rest. It is applied at both request-artifact upload call sites, not in the `artifacts` package: the meta request (client → PicoTera, `gateway_flow.go`) redacts the client's PicoTera key, and the upstream request (PicoTera → provider, `gateway_flow_attempts.go`) redacts the provider credential. Response-artifact cookie redaction is separate (`redactResponseHeaders`, inside `uploadResponseArtifact`).

### Database Schema

Core tables: `provider`, `endpoint`, `provider_endpoint`, `model`, `model_provider_endpoint`, `api_key`, `request` (hypertable), `script`, `traces`, `project`, `app_user`, `user_identity`, `user_session`, `user_setting`. Uses JSONB for flexible fields (provider models, annotations, project paths, setting values). Upsert pattern via `ON CONFLICT DO UPDATE`. `endpoint` carries a `prefix_match BOOLEAN NOT NULL DEFAULT FALSE` (migration 048) — see "Prefix matching" under Key Patterns. The same migration retires the two Codex-only endpoint types (11 `codexCompact`, 12 `codexSearchV1Alpha`) in favour of `codex` = 14: rows still carrying them are reset to `general` (1, not reversible), the wire strings are gone, and the two `contract.EndpointType_*` constants remain only as placeholders so the numbers are never reused (historical `request` rows and migration 047 still reference them). `api_key` / `request` / `traces` / `project` all carry a `user_id` (see "User isolation & authorization"); `app_user` has a `disabled` flag; `user_session` (migration 051, oidc mode only — see "User authentication") is keyed by the random session id and deleted on logout, at login for that user's expired rows, and inside the delete-user transaction; `user_setting` is keyed `(user_id, key)` and holds per-user prefs (e.g. `project.autoCreate`). There is no global-settings table — the dashboard title is an env var and all other settings are per-user in `user_setting`. The `request` hypertable also carries a nullable `project_id` (no FK) populated by the project extractor post-auth. It also has a nullable `annotations` JSONB column (migration 044) whose only writer is the script layer's `SetRequestAnnotation` (see "Annotation API + request refs") — a single-statement atomic read-modify-write per key: a set is `COALESCE(annotations,'{}') || jsonb_build_object(key, value)`, a delete is `NULLIF(COALESCE(annotations,'{}') - key, '{}')` so removing the last key returns the column to `NULL`. `GET /api/picotera/requests?annotations=<url-encoded JSON object>` filters by JSONB containment (`@>`, AND across pairs, exact match) via a **partial** GIN index (`jsonb_path_ops`, `WHERE annotations IS NOT NULL`) so index size scales with tagged rows, not total rows, and INSERT cost is zero (rows are inserted NULL and only ever annotated by that targeted UPDATE; `UpdateRequest` does not touch the column). The annotations filter shares the `filterLookback` (30-day default when `startAt` omitted) with the requestId search. Migration 049 adds three more nullable columns: `tool_usage` JSONB — the upstream-reported tool usage normalized to `[{name, model?, numRequests?, inputTokens?, outputTokens?, numImages?}]` (camelCase, so the column, `RequestView.toolUsage` and the `requestFinished` view are the same shape with no conversion layer) — plus `tool_cost` / `tool_cost_currency`, typed exactly like `model_cost` / `model_cost_currency`. `tool_usage` is extracted by `ResponseExtractor.extractToolUsage`, which runs at the three existing usage-extraction points, keeps only those four whitelisted integer fields, and lets the last non-empty occurrence win. **A zero counter is dropped, not recorded as 0**, and a tool whose four counters are all zero (or that reported an empty object) is dropped entirely — upstreams enumerate the tools they *support*, not the ones that ran, so a Codex response carries a zero-filled `image_gen` every time. "Reported zero" and "not reported" are therefore the same thing by design, which is why `ToolUsageEntry` / `ToolUsageEntryView` use plain `int64 + omitempty` rather than pointers. `model` is looked up in `tools`, the sibling declaration array in the same object (hence `toolUsagePaths` is a table of `{usage, tools}` pairs rather than the plain `[]string` `usageRawPaths` is): `toolDeclaredModel` matches `tools[].type` against the usage key through the `toolUsageToolType` alias table, because the two vocabularies disagree — usage is reported under `image_gen` while the tool is declared as `image_generation`; names absent from the table match verbatim. Of the six `tools[].type` values seen in practice only `image_generation` carries a `model` at all, so an empty `model` is the norm. A declared model never rescues an all-zero entry. Upstreams report `tool_usage` as a **sibling of the format's `usage` object**, so `toolUsagePaths` tries `tool_usage` then `response.tool_usage` (first match wins): Chat Completions / Anthropic / Gemini / non-stream bodies put usage at the payload's top level, while OpenAI Responses SSE wraps both in the event's `response` envelope. Last-wins is load-bearing there — a Responses stream repeats `tool_usage` on `response.created` / `in_progress` / `completed`, and only the last carries the final counts. What lands in the three columns is the extracted usage after the `getToolUsageCost` script hook has had its say (see Scripts): the two success paths (`completeGatewaySuccess`, `unifiedStreamSuccess`) run it once and write one result onto both the upstream and meta rows, and it is the only writer of `tool_cost` / `tool_cost_currency` — the server computes no tool pricing of its own, so both stay NULL unless a script reports a cost. Unlike `annotations` the three have **no index and no filter endpoint** — nothing queries them, so an index would be pure write cost. Migration 050 adds `usage_raw` / `tool_usage_raw`, two more nullable JSONB columns shaped exactly like `tool_usage` (no index, no filter endpoint, written only on the two success paths, one extraction onto both rows) and holding the un-normalized fact: the upstream's own `usage` / `tool_usage` objects verbatim. `captureUsageRaw` scans `usageRawPaths` (`usage`, `response.usage`, `message.usage`, `usageMetadata` — first non-empty object per payload wins, covering all four formats) and `extractToolUsage` records its hit unconditionally, both with **whole-object last-wins** rather than the per-field accumulation the token columns use. Two consequences are by design: an Anthropic stream's `message_delta` usage replaces `message_start`'s outright, so the input / cache breakdown is absent from `usage_raw` while the five token columns still carry it; and `tool_usage_raw` keeps the all-zero entries normalization drops, so it can hold a value while `tool_usage` is NULL. `hasKeys` makes an empty object count as not reported for both (which also stops a top-level `tool_usage: {}` from masking `response.tool_usage`). Unlike `tool_usage` these two never pass through `getToolUsageCost` — they are the record of what the upstream said, so the hook gets them as read-only input and the write takes `ResponseMetrics`' values. Compression compatibility: columnstore has no GIN, so a future `compress_after` must exceed the annotations query window (e.g. 90d vs 30d) to keep the filter on indexed uncompressed chunks. TimescaleDB continuous aggregates (`request_overview_bucketed`, `request_speed_bucketed`, `request_outcome_bucketed`, all 10-minute buckets, `materialized_only = false`) power the overview metrics and group by `user_id`. `request_outcome_bucketed` (migration 045) backs the "成功率统计" charts and the summary success-rate card: unlike the other two it does **not** filter `type = 1` (it covers meta *and* upstream rows) and it adds `type`, `endpoint_path`, `COALESCE(finish_reason, 0)` and `output_tokens = 0` (as `empty_response`) as GROUP BY keys, so one scan feeds the success-rate / empty-reply / finish-reason-share charts. The same migration adds the `completion_endpoint_path` view — the chat/completion endpoint scope shared by those queries and the requests-list `emptyResponse` filter; endpoints outside it (model lists, `count_tokens`, Exa search, Codex search v1alpha, `general`) have `output_tokens = 0` by nature and would otherwise read as failures. Migrations 047 and 048 rebuild the view (`CREATE OR REPLACE`, same column structure; no continuous aggregate depends on it) for the Codex routes. As of 048 it is a three-way union: `endpoint_type IN (2,3,4,7,8)`; plus, for every `endpoint_type = 14` (`codex`) row, `path || '/responses'` and `path || '/responses/compact'` — matching how a prefix endpoint records `prefix + suffix`; plus the same seven constant `/api/unified` paths 047 established (the original five, `/api/unified/codex/responses`, `/api/unified/codex/responses/compact`). Search paths (`path || '/alpha/search'`, `/api/unified/codex/alpha/search`) stay **out**, as does `openaiEmbedding` (13) / `/api/unified/v1/embeddings` — those responses have no output tokens by nature and would read as empty replies. All three halves are explicit whitelists, so a new endpoint type is excluded by default and adding one needs no migration; token / cost / request-volume stats (`request_overview_bucketed` et al.) still count embedding requests.
